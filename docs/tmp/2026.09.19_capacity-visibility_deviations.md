# Capacity visibility — provider-usage journal

Worker: capacity-visibility worktree. Owned paths: `plugins/provider-usage/**`,
this file. Started 2026-09-19.

## Task

Extend the existing BB Provider Usage plugin so the usage surface lists
installed/configured execution providers even when no `provider-usage.v1`
source publishes a resource for them, with an honest "Limits unavailable"
state distinct from "not measured yet". Registered providers must be
discovered dynamically so a later `acp-devin` registration appears without
changes here. No new dashboard, model picker, rotation, or quota invention.

## Source findings (this checkout)

- `plugins/provider-usage/server.ts` `readUsage` aggregates:
  `sdk.hosts.list()` (non-ephemeral) + `sdk.plugins.experimental_discoverRpc`
  for `provider-usage.v1.listResources` + `sdk.providers.list({capability:
"usage"})` for metadata/order only. Rows exist only where a source
  publishes a resource. Measurements are fetched lazily: only when a request
  carries a `providerId`, and only for resources in `machineIds`.
- `provider-usage.v1` contract (`usage-source-contract.ts`): resources carry
  `providerId`, `accountKey` (provider-issued; null = unknown, never merged),
  scope `{kind:"shared"} | {kind:"host",hostId,hostName}`. Measurements
  carry `observedAt` (last _successful_ observation) and a discriminated
  `usage` union: ok / not_installed / unauthenticated / expired / error.
- Existing sources (`provider-codex`, `provider-claude-code`,
  `provider-acp`, `account-pool`) each implement the contract themselves.
  The host-scoped ones enumerate `sdk.providers.list({hostId, capability:
"usage"})` and wrap `sdk.system.usageLimits`; pool wraps shared accounts.
- `sdk.providers.list({hostId})` (server: `listSystemProviderInfosForHost`,
  `apps/server/src/services/system/execution-options.ts`) returns the
  provider registry filtered per host: `visibility:"always"` registrations
  plus `visibility:"installed"` ones whose host health probe reports
  installed (probe results cached server-side). A disconnected host falls
  back to the configured (always) list. This is the dynamic registered-
  provider inventory the feature needs; a provider whose plugin is disabled
  is absent, and `available:false` marks registrations kept after a host
  artifact load failure (`plugin-runtime.ts`).
- `ProviderInfo` (`packages/domain/src/provider-types.ts`) carries
  `maintenance.{health,usage,installation}`, `available`, icon/logoUrl/
  strings — enough for native icons and hints without new core API.
- Per corrected audit `bb/docs/product/provider-support.md`: Cursor via
  `provider-acp` declares `providerUsage` (source resource exists);
  OpenCode/Grok/omp/Hermes ACP entries and the in-flight Devin provider have
  no usage path — these are the rows that gain "Limits unavailable".
- `ProviderUsage` display schema (`usage-schema.ts`) is the plugin's own
  aggregate output; adding a union member is a local change. `usage: null`
  already means "listed, not fetched yet" (lazy tabs).
- CLI: `bb plugin rpc call provider-usage getUsage --input-file <f> --json`
  already reaches the aggregate; `list`/`inspect` exist for discovery. No
  dedicated plugin CLI command exists today.
- Fake host (`@get-bb/plugin-sdk/testing`) stubs `sdk.providers.list`,
  `sdk.system`, `sdk.hosts`, `sdk.plugins` per test — offline tests cover
  all acceptance states without live auth.

## Decisions / deviations

- **No second collector.** An earlier sketch fetched
  `sdk.system.usageLimits` directly for `maintenance.usage` providers lacking
  a resource. Rejected by the parent scope check: `maintenance.usage` is a
  bridge capability flag, not an aggregated resource identity, and a parallel
  fetch/cache path duplicates the source contract's job. This change is
  inventory-only.
- **New display status `unsupported`** in `providerUsageSchema`, emitted by
  the aggregate for a registered provider visible on a host machine that no
  usage-source resource covers. Rendered as "Limits unavailable." — the
  provider cannot be measured through this surface; it does not mean zero or
  unlimited quota.
- **`usage: null` relabeled "Not measured yet."** (was "Usage not reported."
  / "Usage not provided.") — distinguishes a covered resource whose lazy
  fetch has not run (or failed, which separately shows the machine refresh
  notice) from a provider with no measurement path at all.
- Inventory rows are synthesized per host machine only (`source:*` pool
  machines are unchanged), skipped when the providerId is covered by any
  resource on that machine, and dedup/accountKey semantics of
  `selectUsageResources` are untouched. No summing of limits anywhere.
- Disconnected hosts list only their `visibility:"always"` (configured)
  providers — the server's provider listing cannot run install probes while
  offline, so `visibility:"installed"` entries are absent and no listed row
  on a disconnected host is evidence of installation. The machine keeps its
  offline notice. `providers.list` failure for a host degrades to no
  inventory rows rather than breaking the snapshot. The `unsupported`
  inventory state is emitted only for provider rows and stays distinct from
  the account-level `unauthenticated`/`expired` states a measured source can
  still return.
- **Not done (explicitly out of scope after reset):** no new `bb` CLI
  command — existing `bb plugin rpc call provider-usage getUsage` is the CLI
  surface and reads the same server projection. `getUsage` could not be
  marked `experimental_discoverable`: the host rejects discoverable methods
  whose contract schemas lack Standard JSON Schema export (zod/mini here),
  so `bb plugin rpc list` does not show it; the README documents the call.
  No `observedAt`/freshness field on the aggregate schema, no per-provider
  health/installation probing beyond what `providers.list` already does.
- GLM/Z.ai: this surface only ever shows the registered harness/provider
  row (e.g. Devin, OpenCode), never a model route. A GLM model selected
  through such a harness runs on that harness's account and does **not**
  satisfy the separate paid Z.ai subscription requirement, which remains a
  future product item — its authentication, execution, and usage paths are
  unverified and explicitly deferred, not claimed by this change.

## Evidence

- `pnpm exec turbo run typecheck --filter=bb-plugin-provider-usage` — clean.
- `pnpm exec turbo run test --filter=bb-plugin-provider-usage` — 5 files,
  23 tests pass. New server test covers: a registered provider with no
  source resource appears as `usage: {status:"unsupported"}` on its host
  machine; a covered provider keeps its single resource row (no duplicate);
  selecting an unsupported provider issues no `getResource` fetch; a covered
  provider's lazy fetch still fires on selection; `providers.list` is called
  per host id; a disconnected host still lists its configured providers; a
  host whose provider listing fails still renders its resource rows. The
  pre-existing dedup test still proves shared `accountKey` collapse and
  unknown-identity separation.
- UI: jsdom tests assert "Limits unavailable." and "Not measured yet." in
  both the sidebar disclosure (`app.test.tsx` state table) and the settings
  page (`settings.test.tsx`). A `noUsageSource` Ladle scenario mixes
  measured/unmeasured/unsupported rows on one machine for manual visual
  inspection; no live-auth render was performed in this worktree.
- Boundary notes: the aggregate now issues one `providers.list` per
  non-ephemeral host per read (server-side installed-probes are cached);
  `unsupported` exists only in this plugin's aggregate schema — the
  `provider-usage.v1` source contract, its sources, and the SDK are
  unchanged; an inventory row reflects registry visibility, not
  authenticated execution.


## Independent acceptance correction

Fresh Astra review found synthetic unsupported rows counted as prior usage,
causing offline views to claim a cached measurement on the first read. The
integration owner excluded unsupported from reported usage and gives an
unsupported-only selection neutral offline wording, without promising future
quota measurement. Both the compact card and settings have a regression case.
