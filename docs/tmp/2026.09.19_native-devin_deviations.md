## Deviations and surprises (expected / observed / evidence / action / risk)

### 1. `supportsManualCompaction` downgraded to false

- Expected: earlier probe notes claimed Devin advertises `/compact` and the
  declaration initially set `supportsManualCompaction: true`.
- Observed: no `session/update` `available_commands_update` arrives after
  `session/new` or during a prompt; sending `/compact` as a prompt returned
  `end_turn` with zero agent text — indistinguishable from a no-op.
- Evidence: probe output captured during this session (no `available_commands`
  update in a 25 s window; `/compact` prompt finished with empty message).
- Action: flag removed; declaration now reports `false` (BB default).
- Unresolved risk: if a future Devin CLI advertises commands, compaction can be
  re-enabled then.

### 2. Devin's real skill surface is larger than `devin skills paths` reports

- Expected: roots = the printed list (user: XDG devin + cognition +
  `~/.agents/skills`; project: `.devin`, `.cognition`, `.agents` skills).
- Observed (empirical, fake HOME + fake project): also scanned —
  project `.windsurf/skills`, `.cursor/skills`, `.claude/skills`; user
  `~/.claude/skills`, `~/.cursor/skills`. NOT scanned: project
  `.codex/skills`, `.opencode/skills`; user `~/.windsurf/skills`,
  `~/.codex/skills`, `~/.config/agents/skills`, `~/.config/opencode/skills`.
  Scanning is non-recursive (nested `skills/a/b/SKILL.md` not found) and walks
  ancestor directories up to the `.git` root. Devin does not honor a
  `.claude-plugin/plugin.json` skip marker.
- Action: declared project roots `.devin/skills`, `.cognition/skills`,
  `.agents/skills`, `.windsurf/skills`, `.cursor/skills`, `.claude/skills`
  (all `ancestors: true`, non-recursive); declarative user roots
  `~/.agents|claude|cursor/skills`; resolver adds the XDG-dependent
  `<XDG_CONFIG_HOME|~/.config>/devin| cognition/skills` roots. Plain
  `.claude/skills` (no `skipIfManifest`) to match Devin's actual scanning.
- Unresolved risk: undocumented roots may change across CLI versions; the
  declared set mirrors version 3000.10.31 behavior only.

### 3. No `permissionCli` mapping

- Expected: permission modes might map to a launch flag.
- Observed: `devin acp --permission-mode` errors (`unexpected argument`).
- Evidence: `devin acp --help` output.
- Action: no `permissionCli`. BB "full" auto-allows the agent's
  `session/request_permission` calls; BB "accept-edits" forwards them to the
  user interaction path. The bridge never writes Devin's `mode` config option,
  so the session stays in Devin's `accept-edits` mode; Devin's `bypass` mode is
  never selected by BB.
- Unresolved risk: Devin's in-mode auto-approvals (workspace edits under its
  own `accept-edits` policy) bypass BB's permission UI. This matches the
  generic ACP mechanism but is worth noting for reviewers.

### 4. Generic icon (no custom mark)

- Expected: a Devin logo might be reconstructed.
- Observed: per user direction, logo tracing was stopped; the shipped-agent
  logo test requires declared plugin icon assets, so `icon` is omitted.
- Action: `acp-devin` registers with `logoUrl: null` and no glyph — the
  cosmetic limitation: Devin shows a generic fallback in the picker.
- Unresolved risk: none functional; cosmetic only.

### 5. Capability claims kept conservative

- fork: `none` (no `session/fork` in `sessionCapabilities`).
- Resume: `loadSession: true` and `sessionCapabilities.list`/`delete` exist;
  the bridge supports `session/load` generally. Actual BB-level resume was not
  separately exercised in these probes; declared support relies on the
  bridge's load path, reported as untested if not covered by the smoke.
- Usage reporting / account switching / quota / rotation: not claimed
  (`providerUsage`/`providerInstallation` unset → `maintenance.usage: false`,
  `maintenance.installation: false`). Devin emits `usage_update`
  notifications, but no provider-maintenance claim is made from that.
- Models: `primaryModels` = `adaptive`, `swe-2-high`, `claude-opus-5-medium`,
  `gpt-5-6-sol-medium` — all verified present in the live `session/new` model
  option. Full catalog discovery is ACP-native via `configOptions`.
  Note (per audit): ACP model selection can silently skip an unknown model ID
  and filesystem confinement applies only to bridge-mediated writes — the docs
  make no broader claims about either.

### 6. Service-tier capability override (parent-directed)

- Expected: `declaration.ts` inherited `supportsServiceTier: true` plus
  `serviceTiers` [Default, Fast] for every ACP agent.
- Observed (independent review): Devin's `session/new` advertises only `mode`
  and `model` config options — no `fast` option — so
  `selectAcpNativeServiceTier` in the bridge silently no-ops; the UI claim was
  dishonest for Devin.
- Action: added optional `supportsServiceTier?: boolean` on
  `AcpAgentDefinition` (absent = true, preserving all other agents);
  `declaration.ts` omits `serviceTiers` and sets the capability false when the
  agent opts out; `acp-devin` sets `supportsServiceTier: false`. Regression
  tests assert devin has no tiers/false capability while `acp-cursor` keeps
  `["default","fast"]` and `supportsServiceTier: true`.
- Unresolved risk: other ACP agents were not re-probed for a `fast` config
  option; the same audit may apply to them (out of this lane's scope).

### 7. Edit scope extended beyond `plugins/provider-acp/**`

- Expected: changes confined to the plugin (plus packages/** if required).
- Observed: adding a known agent changes the registered provider list, which
  several repo tests enumerate exactly; user-facing enumerations in docs also
  list shipped agents.
- Action (all disclosed, no product logic touched):
  - `apps/server/test/**` — added `acp-devin` to provider enumerations and
    installed-only fixtures; added a launch-spec case in
    `thread-runtime-config.test.ts`. Required: these tests fail otherwise.
  - `docs/configuration.md`, `packages/bb-app/README.md`,
    `packages/templates/src/templates/bb-guide-providers.md` — added `acp-devin`
    to agent/skill-root tables. Flagged for parent review: the brief said
    canonical product docs are parent-owned; these are discoverable-user-doc
    surfaces that would otherwise be stale. Revert if the parent prefers.
  - No `packages/provider-bridge-acp` or plugin-sdk changes were required —
    the existing generic ACP launch-spec/permission/model paths suffice.
