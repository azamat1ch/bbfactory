# factory-slice deviations and decisions

Journal for Outcome B (first native one-task delivery slice). Format:
expected / observed / evidence / action / unresolved risk.

## Native integration seam (chosen, with source evidence)

Chosen seam: **direct `bb.sdk.threads.spawn` with plugin-attributed ownership
metadata**, owned by the bbfactory server plugin — not a cross-plugin
Workflows dependency.

- `bb.sdk.threads.spawn` accepts `projectId`,
  `environment: { type: "reuse", environmentId }`,
  `lifecycleOwnerThreadId`, `pluginMetadata`, `providerId`, `model`,
  `reasoningLevel`, `permissionMode`, `visibility`
  (`packages/server-contract/src/api/threads.ts` `createThreadRequestSchema`,
  used by `plugins/workflows/src/service.ts`).
- When a plugin supplies `pluginMetadata`, the server forces
  `origin: "plugin"` + `originPluginId: <pluginId>`
  (`apps/server/src/services/plugins/plugin-api.ts` ~line 328;
  `packages/plugin-sdk/src/backend-contract.ts` ~line 2066;
  mirrored by `packages/plugin-sdk/src/testing/fake-sdk.ts`
  `withThreadAttribution`). This gives bbfactory reliable ownership
  attribution for discovery/reconcile:
  `threads.list({ originPluginId, includeHidden: true })`
  then `threads.getPluginMetadata({ threadId })` — the same pattern
  Workflows uses for its workers.
- Workflows exposes no documented cross-plugin service API, and its stop
  helper / retry paths do not prove exclusive-writer safety, so the serial
  slice keeps one bbfactory-owned lifecycle instead of delegating worker
  ownership to it.
- Independent checks cannot run in QuickJS workflows (no shell/filesystem),
  so they run in a bbfactory host entry via `bb.hosts.experimental_client`,
  resolved server-side from the originating thread's environment
  (`thread.environmentId` → `sdk.environments.get` → `hostId` + absolute
  `path`).

## Corrections applied during implementation

### Spawn exceptions are not confirmed failure

- Expected: a failed `threads.spawn` call means no writer exists.
- Observed (parent correction): a lost transport reply can leave a live
  writer; `spawn` throwing is not proof of failure.
- Action: launch intent + ownership metadata are persisted BEFORE spawn; a
  spawn exception marks the attempt `uncertain` (not `failed`) and the task
  `blocked`. `uncertain` holds workspace ownership; the reconciler
  re-discovers matching native threads by originPluginId + pluginMetadata
  (including archived ones — `threads.list` `archived` is tri-state and is
  omitted so archived orphans are still found) and either attaches them as
  `running` or stops them when the task is already `cancelling`.
- Evidence: `plugins/bbfactory/src/service.ts` `startAttempt`,
  `discoverWorkers`, `attachDiscoveredWorker`; `service.test.ts` lost-reply
  and reattach cases.

### No abandon; ownership is workspace-scoped

- Expected (earlier draft): an explicit `abandon` could release ownership.
- Observed (parent correction): abandon is not authorized; ownership is
  scoped to the workspace across all tasks, and unresolved cancels stay
  pending.
- Action: no abandon operation exists. One active writer per
  `(host_id, workspace_path)` across all tasks, enforced by a partial
  UNIQUE index (`factory_attempts_workspace_owner_idx`) so the claim is
  atomic even under concurrent `startAttempt` calls — the pre-check only
  produces a friendlier error. `completed` and `verifying` stay in the
  active set so no new writer or check can overlap the verification
  snapshot; verification ends in terminal `verified`.
- Evidence: `plugins/bbfactory/src/data.ts` migration +
  `getActiveAttemptForWorkspace` + `transitionAttemptState`;
  `service.test.ts` "workspace claim is enforced atomically" and
  "ownership survives verification" cases.

### Archived is not terminal proof

- Expected: `archivedAt !== null` means the writer is gone.
- Observed (Astra review): `thread-archive.ts` calls
  `requestThreadStopForCurrentState` fire-and-forget before emitting
  `thread.archived` — an archived writer may still be running.
- Action: only `deletedAt !== null` or status `idle`/`error` count as
  terminal. `archived` keeps ownership, requests a stop for delegate
  workers, and is never silently applied to the lead thread for direct
  attempts.
- Evidence: `apps/server/src/services/threads/thread-archive.ts`
  `archiveThreadWithLifecycleEffects`; `service.ts`
  `handleWorkerTerminal`, `pollLiveWorkers`, `isWriterTerminal`.

### Manual completion requires a confirmed terminal writer

- Expected: `factoryCompleteAttempt` could record worker completion on
  request.
- Observed (review): it released ownership without proving the thread was
  idle/stopped.
- Action: `completeAttempt` reads the writer thread and only records
  completion when it is terminal; otherwise the call is rejected and the
  attempt keeps the workspace. Cancelling a direct attempt no longer
  releases ownership immediately and never stops the user's lead thread —
  it stays `cancelling` until the lead reaches a terminal state.
- Evidence: `service.ts` `completeAttempt`, `cancelTask`;
  `service.test.ts` "manual completion while the worker is still active"
  and "cancelling a direct attempt" cases.

### Evidence capture fails closed

- Expected: capture hashed any file and skipped unreadable entries
  silently; files >64MiB were recorded by size only.
- Observed (review): same-size-only entries and silently skipped
  directories could pass changed content off as verified; the walker also
  traversed dependency/build trees up to 256MiB.
- Action: the walker uses an explicit exclusion set (`.git`,
  `node_modules`, `dist`, `build`, `target`, `vendor`, venvs, caches…) but
  still descends into excluded directories that contain git-tracked files
  and hashes tracked files under them, plus file mode. Unreadable
  files/directories, oversize files, and cap hits all record
  `incomplete` + `incompleteReasons`, and the service blocks rather than
  accepts on any incomplete snapshot. `runCheck` reports
  `processTreeSettled` (fail-closed false on Windows/unsupported); a check
  whose killed process tree does not settle within 10s marks its evidence
  `incomplete`, halts the attempt, and keeps workspace ownership — an
  explicit cancel cannot release it either (same unknown-writer
  invariant).
- Evidence: `plugins/bbfactory/src/host.ts` `collectEntries`,
  `processGroupSettled`; `service.ts` `runVerification`; `host.test.ts`
  exclusion/oversize/unreadable/mode/tracked-under-excluded cases.

### Accepted state is reconfirmed after restart

- Expected: an `accepted` task could be re-shown as accepted after a
  plugin restart.
- Observed (review): the workspace may have changed while the plugin was
  down, and a failed watch arm leaves post-acceptance drift undetected.
- Action: `recoverAfterRestart` recaptures accepted workspaces, compares
  against `acceptedFingerprint`, marks evidence stale + blocks on
  mismatch, incomplete capture, recapture failure, or a watch that cannot
  be armed. Live acceptance also fails closed if the watch cannot arm.
- Evidence: `service.ts` `recoverAfterRestart`; `service.test.ts`
  restart cases.

### Bug fixed: stale row passed to stop

`attachDiscoveredWorker` updated `workerThreadId` then called
`requestWorkerStop` with the pre-update row (null id → early return, so a
discovered writer under a cancelling task was never stopped). Now fetches
the updated row first.

### A requested stop / failed / deleted writer is not proof of no writers

- Expected: once the writer thread reports `idle`/`error`/`deleted` after
  a stop request, the workspace is safe to hand to a new writer.
- Observed (parent's native Devin smoke): a requested stop returned
  `idle`/`interrupted` while the writer's detached `sleep` survived. No
  SDK call can currently prove the process tree is dead.
- Action: writers that end non-organically — stopped by request, failed,
  deleted — transition the attempt to `halted`, which stays in the
  ownership set forever in this slice. Cancelling a `halted` attempt
  marks the task `cancelled` but does not release the workspace. Only
  organically finished writers release: `verified` (checks ran) or
  `settled` (direct lead turn finished organically before cancel, or a
  `completed` attempt cancelled).
- Evidence: `service.ts` `settleCancelled`, `haltAttempt`,
  `settleAttempt`, `cancelTask`; `service.test.ts` cancel cases assert
  `halted` and that a second task's `startAttempt` still rejects with
  "live writer".

### Lost check RPC / restart mid-check / unsettled trees retain the lease

- `runCheck` throwing (lost reply, host crash) records the evidence
  `incomplete` — the check process may still be alive — stops running
  subsequent checks, and the attempt halts rather than releasing.
- Any `incomplete` evidence in a verification run dominates every exit
  path (post-capture incomplete, spec change, content change, cancel,
  RPC error): the attempt transitions `verifying → halted` and keeps the
  claim.
- `recoverAfterRestart` marks evidence left `running` by a restart
  `incomplete`, halts its attempt, and blocks the task instead of
  silently rerunning a check whose first incarnation may still be alive.
- Evidence: `service.ts` `runVerification` finishBlocked ordering,
  `recoverAfterRestart`; `service.test.ts` "a lost runCheck reply halts
  the lease", "restart with a check in flight halts", "unsettled check
  process tree keeps workspace ownership even through cancel".

### Reconcile queue race fixed

- `reconcileOnce` previously returned the in-flight promise to a later
  caller, so a caller could observe a pass that started before its
  trigger (e.g. a worker appearing after discovery ran). Now a call
  during an in-flight pass schedules one more pass before resolving.
- Evidence: `service.ts` `runReconcile`/`reconcileOnce`; the two
  previously-flaky reconcile tests.

## Remaining gaps / unresolved risks

- `threads.get` on a deleted writer thread may throw rather than return
  `deletedAt`; polling records "status unknown" and relies on the
  `thread.deleted` event for terminal settlement.
- A `halted` workspace claim has no release path in this slice —
  releasing requires verified-stop evidence the SDK cannot provide (no
  process-tree query for arbitrary writers). Documented limitation, not a
  bug: the workspace stays claimed rather than risk overlapping writers.
- Direct-mode completion still keys on the lead thread's `idle` event, so
  any lead turn ending counts as writer completion; acceptable for the
  serial slice.
- `pluginMetadata` discovery requires `getPluginMetadata` per listed
  thread; bounded by `WORKER_DISCOVERY_LIMIT` (500).
- Check argv runs with the host's sanitized env; no per-task env support.
